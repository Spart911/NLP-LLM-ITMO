# Отчет

## Цель

Собрать пайплайн, в котором модель переводит фразу на естественном языке в параметры поиска, а обычный код проверяет эти параметры и читает каталог SQLite. Отдельно обрабатываются ошибка разбора, журнал шагов и уточнения, состояние которых хранится в программе.

## Архитектура

Запрос проходит фиксированные стадии. Модель не пишет и не выполняет SQL.

1. `ChatPromptTemplate` собирает системное сообщение и реплику пользователя.
2. Клиент OpenAI-совместимой модели вызывает LLM. Режим размышления по умолчанию выключен. В сравнении 2.4 он включается явно.
3. Парсер забирает текст ответа. Для категории товара это `StrOutputParser`. Для параметров поиска это `PydanticOutputParser` и модель `ProductQuery`: `category` (`laptop`, `smartphone`, `tablet`, `other`), `max_price` (`null` или целое не ниже нуля), `sort_by` (`price_asc`, `price_desc`).
4. При ошибке разбора `with_retry` повторяет только промпт, вызов модели и парсер. Предел — три попытки. Поиск в эту границу не входит.
5. Функция поиска принимает уже проверенный `ProductQuery`. Для `other` SQL не строится. Иначе запрос параметризованный: категория и потолок цены подставляются через `?`, направление сортировки берется из белого списка `ASC`/`DESC`.
6. Журнал пишет старт модели, разбор, проверку, подтверждение и поиск.
7. В диалоге программа хранит последний верный `ProductQuery`. Неудачный разбор его не затирает.

Каталог: 24 товара, по 8 в каждой из трех категорий. У строки есть id, название, бренд, категория, цена и остаток.

### Классификация

Прямой вызов модели вернул `AIMessage`. Цепочка промпт–модель–`StrOutputParser` вернула `TextAccessor`. Это строка: да. Пакет из трех формулировок тоже состоит из строк.

| Нужен смартфон с хорошей камерой | русский | Смартфоны. Это категория мобильных устройств, где ключевым критерием выбора является качество встроенной фототехники. |

### Поиск по каталогу

Цепочка после разбора вызывает поиск. Десять запросов ниже. Для двух размытых фраз эталона нет: отметка «да» значит, что строки базы согласованы с полученными параметрами. `other` дает пустой список и сообщение, что категория не поддерживается.

### Повтор и журнал

Кривые ответы разбирались на подставной модели, чтобы ошибка была воспроизводимой. Подробности — в разделах про ошибки и журнал.

### Уточнения

Два диалога по три реплики прогнаны в двух режимах. Цифры — в сравнении 5.2. Короткое состояние сохранило поля на всех шагах. Полная история на третьей реплике обоих диалогов потеряла потолок цены.

## Сравнение 2.4. Режим размышления

Одни и те же два размытых запроса отправлены с выключенным и включенным рассуждением. Парсер читает только `content`.

| Запрос | Режим | Параметры | Время, с | Вход | Выход | Из них рассуждение | Разбор content |
|---|---|---|---:|---:|---:|---:|---|
| Конспекты и фильмы, тысяч до тридцати | выкл. | tablet, 30000, price_asc | 1.062 | 538 | 35 | 0 | успешен |
| Конспекты и фильмы, тысяч до тридцати | вкл. | tablet, 30000, price_asc | 1.876 | 562 | 142 | 115 | успешен |
| Нормальный экран в карман, не самый дешевый | выкл. | other, null, price_asc | 0.884 | 533 | 30 | 0 | успешен |
| Нормальный экран в карман, не самый дешевый | вкл. | smartphone, null, price_asc | 4.416 | 557 | 427 | 403 | успешен |

Без рассуждения `content` — это JSON. С рассуждением `content` тоже JSON, а текст рассуждения лежит отдельным полем и в `content` не входит. Поэтому парсер оба ответа разбирает. Если бы рассуждение попало в ту же строку, это уже был бы не JSON.

На втором запросе включенное рассуждение сменило категорию с `other` на `smartphone`. Порядок при этом остался `price_asc`: формулировка «не самый дешевый» в поля не перешла. Включенный режим дороже по времени и по выходным токенам: 0.884 с и 30 токенов против 4.416 с и 427 токенов.

## Сравнение 3.4. Инструмент и текстовая схема

Текстовая цепочка описывает `ProductQuery` инструкциями формата в системном промпте. Модель пишет JSON в `content`, парсер достает поля, Pydantic их проверяет, программа вызывает поиск.

У инструмента схема — аргументы `search_products`, они передаются через `bind_tools`. Вызов из ответа разбирает сервер провайдера и кладет его в `tool_calls`. Приложение проверяет `args` через `ProductQuery` и само выполняет SQL. Результат поиска модели не отправляется.

| Найди ноутбуки дешевле 70 000 рублей | пусто | search_products, laptop, 70000, price_asc | да, после проверки |
| Покажи самые дорогие смартфоны | пусто | search_products, smartphone, price_desc | да, после проверки |
| Хочу посмотреть планшеты | пусто | search_products, tablet | да, после проверки |

## Повтор и фрагмент журнала

Подставная модель сначала отвечает текстом `это не json`, затем верным JSON ноутбуков до 70 000.

Без повтора одна попытка, журнал `llm_start → parse_error → stopped`, поиск не вызывался.

С повтором вторая попытка верная. Журнал:

```
llm_start, attempt 1
parse_error, attempt 1, OutputParserException / JSONDecodeError
llm_start, attempt 2
parsed, attempt 2, laptop / 70000 / price_asc
validation, ok
search, found 5
```

Поиск стоит после проверки и встречается один раз. Найдено 5 ноутбуков.

Три неверных ответа подряд: три `parse_error`, затем `stopped`. Сообщение: «Не удалось разобрать параметры запроса за 3 попытки. Поиск по каталогу не выполнялся.» Поиска в журнале нет.

Отдельный прогон с верным JSON планшета без потолка цены получил отказ подтверждения. Журнал: `llm_start → parsed → validation → confirmation → search_skipped`. Поиск не выполнялся.

## Три ошибки разбора

Все три примера парсер оборачивает в `OutputParserException`. Исходная причина лежит в `__cause__` и от этапа зависит.

1. Текст `это не json`. Причина `JSONDecodeError`. Ошибка на разборе текста в JSON, до проверки полей `ProductQuery`.
2. JSON с `category` равным `fridge`. Причина `ValidationError`. JSON уже получен, поле не входит в `laptop`, `smartphone`, `tablet`, `other`.
3. JSON с `max_price` равным `-5`. Причина `ValidationError`. JSON уже получен, срабатывает ограничение `max_price >= 0`.

Строка с числом в кавычках, например `"50000"`, ошибкой не является: Pydantic приводит ее к целому. Поэтому в примеры она не бралась.

## Выводы

Цепочка с `StrOutputParser` возвращает строку, а цепочка с Pydantic — проверенный объект, пригодный для поиска. Пять запросов с эталоном разобраны без расхождений. «50 тысяч» стало числом 50000, холодильник стал `other`.

Рассуждение увеличивает время и число выходных токенов. В `content` при этом остается JSON, и парсер его читает. На одной размытой фразе включенное рассуждение сменило категорию, но не порядок сортировки.

Поиск детерминирован: одни и те же параметры дают одни и те же строки. Модель без базы не назвала товары каталога и не отличила пустую выборку ноутбуков дешевле 20 000 от непустой. Вызов инструмента переносит схему в `tool_calls`, но проверку и SQL оставляет программе. На приветствие инструмента не было, и поиск не стартовал.

Повтор имеет смысл только вокруг генерации и разбора. Журнал показывает, что база открывается после успешной проверки и не открывается ни при исчерпании трех попыток, ни при отказе от поиска без потолка цены.

Для уточнений короткая память параметров на этих диалогах надежнее полной истории: третья реплика истории сбрасывает потолок цены и порядок, а входных токенов требует больше.

## Ответы на контрольные вопросы

1. Здесь порядок стадий задан программой. Модель переводит фразу в параметры и не получает результат поиска, поэтому не выбирает следующий шаг. Агент сам выбирает функцию и решает, что делать с ее результатом.
2. Цепочка собирается оператором `|` из промпта, модели и парсера. `StrOutputParser` забирает текст ответа. В прогоне прямой вызов вернул `AIMessage`, цепочка — строку `TextAccessor`.
3. Системное сообщение задает роль и правила, включая формат ответа. Пользовательское сообщение содержит запрос. Так инструкция не смешивается с фразой, которую нужно разобрать.
4. Структурированный ответ имеет фиксированные поля и проходит проверку схемы. Произвольный текст таких полей не задает, и подставить его в поиск нельзя.
5. `BaseModel` описывает объект. `Field` задает смысл поля, значение по умолчанию и ограничение, например цену не ниже нуля. `Literal` разрешает только перечисленные значения категории и сортировки.
6. Без базы у модели нет строк каталога. На три вопроса о товарах она не назвала ни одного имени из базы и не знала, что ноутбуков дешевле 20 000 в ней нет.
7. В текстовой схеме модель пишет JSON в `content`, а парсер достает поля из этого текста. У инструмента сервер провайдера кладет вызов в `tool_calls`. Приложение в обоих случаях само проверяет `ProductQuery` и выполняет SQL. Выборка модели не возвращается.
8. Проверка до базы не пускает в SQL чужую категорию и отрицательную цену. Запрос собирает программа: значения идут параметрами, направление сортировки берется из белого списка. SQL, написанный моделью, не исполняется.
9. Повтор ловит `OutputParserException`: битый JSON, значение вне перечисления, нарушение числового ограничения. `with_retry` заново вызывает ту же цепочку и не показывает модели текст прошлой ошибки. Поиск при повторе не выполняется. Предел — три попытки.
10. Состояние хранит программа: последний верный `ProductQuery` и список реплик. На шаге модели уходит либо этот JSON, либо вся история, плюс новая реплика. Ошибочный разбор сохраненные параметры не заменяет.
